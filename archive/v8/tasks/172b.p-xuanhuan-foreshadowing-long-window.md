## 1. 现象

172b xuanhuan 实跑到 **Ch65/100** 后主动停跑冻结现场：

这不是 Ch100 终判，但已经超过 sci-fi 同章尺度，并接近/超过 sci-fi Ch100 基线（168），按 `tasks/172b-xuanhuan-ch100-climb.md` §3/§4 纪律停止爬坡并路由 172b.p。

## 2. 根因

诊断脚本 `.tmp/diagnose_172bp_overdue.py` 对 live DB `.tmp/task172b_xuanhuan_ch100.db`（project `1e7ce627...`）的 Ch65 冻结现场统计：

| 指标 | xuanhuan Ch65 | sci-fi Ch65 对照 |
|---|---:|---:|
| planted <= Ch65 | 191 | 143 |
| resolved | 0 | 0 |
| 平均 planted / chapter | **2.94** | **2.20** |
| horizon 主峰 | +12（168/191） | +1/+2/+3 |
| overdue @Ch65 | **171** | 129（vdim 插值口径约 126） |

结论：

1. **不是 resolved 记账链在 xuanhuan 独坏**：sci-fi 对照同样 resolved=0，V7 基线本身主要靠较低 plant 密度 + 既有 due/overdue 口径通过。
2. **172a.p floor=12 确实生效**：168/191 条 horizon 正好是 +12；短窗口 S 维度因此过关。
3. **floor=12 是短窗口修复，不足以覆盖 Ch100 长窗口**：xuanhuan plant 密度比 sci-fi 高约 34%，在无 resolved 的现有 MVP 架构下，overdue 必然线性追上并超过 sci-fi 同章尺度。

因此 172b.p 的最小修复是把 xuanhuan 的 **Ch100 长窗口 horizon floor** 从 12 提升到 48。模拟当前 Ch65 已 planted 数据：

| floor | overdue@Ch65 | overdue@Ch100（仅当前已 planted） |
|---:|---:|---:|
| 12 | 172 | 191 |
| 24 | 135 | 191 |
| 36 | 91 | 191 |
| **48** | **50** | **167** |
| 50 | 41 | 163 |

`floor=48` 是满足 Ch100 `overdue <= sci-fi Ch100 168` 的最小安全档之一；后续 Ch66+ 新 planted 伏笔在 Ch100 前不会变 overdue，因此不会继续抬高 Ch100 overdue。

  - scifi floor=0 no-op 不变

### live DB 修复

对 `.tmp/task172b_xuanhuan_ch100.db` 中 live project 的未 resolved xuanhuan 伏笔执行一次性修复：

```sql
UPDATE foreshadowings
SET expected_resolve_chapter = planted_in_chapter + 48,
    status = 'planted'
WHERE project_id = '1e7ce6279b224e7f8e476f6f4e963417'
  AND status != 'resolved'
  AND expected_resolve_chapter IS NOT NULL
  AND expected_resolve_chapter < planted_in_chapter + 48;
```

说明：

- 只抬高 horizon，语义与 172a.p `_clamp_foreshadowing_horizon` 一致。
- 重置 `status='planted'` 是因为 due/overdue 状态由 `expected_resolve_chapter` 派生；expected 被抬到未来后，旧 overdue 状态已过期。
- 不修改 sci-fi 基线 DB，不修改 `vdim_compare.py`，不降低验收门槛。
