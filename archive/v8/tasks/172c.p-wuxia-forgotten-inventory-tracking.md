## 2. 根因

### 2.1 扣分账（Ch24 continuity report）

health 公式（`continuity_auditor/__init__.py:_compute_health_score`，Ch≤30 factor=1.0、floor=3.0）：

| 构成 | 计数 | 扣分 |
|---|---:|---:|
| orphaned_settings（全 background） | 8 | 8 × 0.1 = 0.8 |
| **forgotten_items** | **23** | `_diminishing_count(23)` × 0.5 ≈ **6.8** |
| overdue_foreshadowings | 0 | 0 |
| state_mismatches | 79 | **0**（Task 171r 已移出计分，Tier 2 观测噪音） |

10 − 0.8 − 6.8 = 2.4 → floor → **3.0**。health 低的唯一实质来源是 **forgotten_items=23**。

### 2.2 forgotten_items 是粒度伪影，不是真遗忘

wuxia live DB 中 23 条 forgotten 的 `item_name` 全是**主角持有物的聚合清单变体**：

```
持有断刀、断刀门刀谱、血书、断刀令（两块铁牌）、刀谱最后一页密文
持有断刀、断刀门刀谱、血书、断刀令（两块铁牌）、刀谱最后一页密文、从暗卫首领处缴获…
```

代码链（`settlement_extractor/_apply.py` §5.2）：

```python
if "inventory" in field_lower or "物品" in field_lower or "道具" in field_lower:
    track_id = f"inv-{project_id}-{uuid.uuid4().hex[:8]}"
    await inventory_repo.create(..., item_name=update.new_value[:50], ...)
```

- 每次 settlement 对 inventory 字段**无条件 create 新记录**（`item_name` = LLM 写的聚合清单截 50 字）
- repo 已有的 `update_last_used()` **从未被调用**——旧记录 `last_used_chapter` 永久冻结
- `_find_forgotten_items` 纯按 `last_used_chapter >= 3 章未刷新` 判定，不做正文回查
- 于是每章一条新聚合串，旧串 3 章后 forgotten → 23 条 → 6.8 分

但断刀/刀谱/血书在正文里**频繁出现**（主角核心道具），不是真被遗忘。

### 2.3 与 xuanhuan 的对照（同深度 Ch24）

| 指标 | xuanhuan | wuxia |
|---|---:|---:|
| health | 8.8 | 3.0 |
| forgotten_items | **0** | **23** |
| orphaned | 13 | 8 |
| state_mismatches | 29 | 79（不计分） |

xuanhuan 的 settlement inventory 是单物品短值，未触发；wuxia LLM 习惯聚合清单，触发写入层缺陷。

### 2.4 修复分层的动机

- **写入层（A2）**是主根因：无条件 create + 从不刷新。修好后新数据是单物品粒度且重复出现即刷新。
- **检测层兜底（B）**覆盖 A2 够不着的失败模式：物品在正文被使用了，但 settlement LLM 当章没写 inventory 更新（漏记）→ `last_used` 不刷新 → 假 forgotten。与 172b 引号 matcher 修复语义一致（正文真实使用应被记账）。
- **存量数据**：23 条聚合串需一次性修复（合并 + 按正文回刷），其回查逻辑与 B 层同源。

### 2.5 实证补充（修复后复核，B 方案依据）

按 §3.1-§3.3 初版修复落地后对 wuxia live DB 逐条复核 11 条残留 forgotten：

- **9 条 ungroundable 碎片/伪名**：核心名在全 25 章 accepted 正文零命中——50 字截断碎片（「从暗卫首领处缴」「从暗卫首领」「铁匣（内有」来源串）、状态陈述伪名（「已取走断刀门密匣」×3）、正文从未书写的名字（「密室三把钥匙之一」×3、「刀谱最后一页密文」）。这些记录永远无法被正文回查刷新，一旦超阈值就是永久 health 拖累 → 删除。
- **1 条复合名短称漂移**：「断刀门刀谱」全名 ch7 后零命中，但正文以短称推进同一 McGuffin（断刀+刀谱 在 Ch20/23 同章共现）→ 多 token 共现匹配挽救。
- **5 条真实静默（残留，非伪影）**：血书（ch19 后零提及）、密函（ch14 登记但正文自 ch4 起未再提及——settlement 幻觉式再登记）、铁匣（ch14 后零提及——一次性道具）、刀谱残页 ×2（ch16 后零提及，跨 character_id 重复登记）。这些是真遗忘信号，health 指标设计上就应捕获。

**结论**：粒度伪影约占 23 条中的 17 条；修复后 health 上限 ~7.2，原文档「回正 ≥8.0」的预期基于「全是伪影」的不完整诊断，不可达。health 门槛与 wuxia 体裁的校准问题转入 172c.q 评估（§6）。

## 3. 修复范围

### 3.1 写入层：`_apply.py` inventory 拆分 + 去重 + 刷新

对 `settlement.character_updates` 中 inventory 类字段的 `new_value`：

1. **拆分单物品**：按 `、` `，` `，` `；`***/*** 切分；括号（`（）()`）内的分隔符不切；剥除「持有/携带/缴获/从…处缴获」等前缀；过滤低信息量碎片（len<2、纯助词）。
2. **同名匹配**：与该项目该角色已有 `status='held'` 记录按归一化物品名匹配：
   - 命中 → `update_last_used(track_id, chapter_number)` 刷新，不新建
   - 未命中 → create 新记录（保持现有 track_id 生成规则）
3. 不匹配 inventory 语义的字段（location 等）路径不变。

### 3.2 检测层兜底：`_find_forgotten_items` 正文回查

对每个 `last_used` 超阈值的候选 item：

- 提取物品核心名（复用 172b 引号 matcher 的 split 集 + low-info 过滤 + `len>=2` 约束）
- 在近 `threshold` 章 accepted 版本正文中出现 → 调用 `update_last_used` 刷新，且不计入 forgotten
- 未出现 → 保留 forgotten 判定（真遗忘仍被捕获）
- **多 token 共现（B 方案）**：复合名（CJK 片段 len>=4）除 full-term 外，生成 2-4 gram token；≥3 个不同 token 且至少一个 len>=3 同章共现即视为使用（复用 172b `_has_multi_token_setting_reference` 语义）。短名只走 full-term 路径，单 token 命中不构成使用——scifi/xuanhuan 的 FP 刷新风险被这两条约束压住。

性能：continuity 审计每 3 章跑一次，候选数十条 × 近 3 章正文（~3500 字/章）字符串搜索，成本可忽略。`continuity.forgotten_threshold` 仍走 `GenreRuntimeProfile`（172h 已接线），本修复不改阈值。

### 3.3 wuxia live DB 存量修复

对 `.tmp/task172b_wuxia_ch100.db`（project `7fcab6ef…`）：

1. 备份 `.tmp/task172b_wuxia_ch100.pre172cp.db`
2. 修复脚本 `.tmp/repair_172cp_inventory.py`：
   - 聚合串记录按 §3.1 拆分规则展开为单物品
   - 同名合并（保留最早 acquired_in_chapter）
   - 按 Ch1-25 accepted 正文回刷各物品 `last_used_chapter`
   - **删除陈旧 ungroundable 记录（B 方案）**：核心名全文零命中且已超阈值的记录（截断碎片/LLM 伪名，永远无法被正文回查刷新）；新鲜登记即使暂无命中也保留
3. 重算验证：forgotten 计数、health 分
