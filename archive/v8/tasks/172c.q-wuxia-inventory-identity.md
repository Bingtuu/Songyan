### 1.1 状态演进写进物品名 → 变体记录堆积

## 2. 根因

172c.p 修的是**记录粒度**（聚合 → 单物品）与**检测兜底**（正文回查），但写入层的**物品身份判定**仍是朴素全名匹配：

```python
norm = _normalize_item_name(item_name)   # 全名（含状态描述、括号备注）
existing = held.get(norm)                # 状态变体永不命中 → 每章新建
```

物品身份的正确抽象是**基底名**（首个括号前的核心名词）：「断刀（裂纹上百道）」与「断刀（濒临碎裂）」是同一物品的不同状态快照，「断刀」与「断刀门刀谱」「断刀令」是不同物品。

三个缺陷在写入层同源：**身份判定缺失**（§1.1——无基底名抽象，变体名永不命中已有记录）与**入库纪律缺失**（§1.2 无长度/形态校验、§1.3 无状态流转）都发生在 `_apply.py` 的同一登记路径上——该路径目前「LLM 写什么就存什么」，没有任何语义闸门。

## 3. 修复范围

### 3.1 写入层：基底名身份匹配（`_apply.py`）

inventory 拆单物品后，匹配逻辑从「全名精确匹配」扩展为两级：

1. **全名归一化匹配**（现状保持）
2. **基底名匹配**：`base = 首个 （/( 之前的片段`，与已有 held 记录的基底名相等 → 命中

命中 → `update_last_used` 刷新，**不新建、不改写 item_name**（首次登记名即身份，变体名只作刷新证据；避免记录名随状态漂移导致正文回查 term 不稳定）。未命中 → create（现状保持）。

**为什么不做前缀匹配**：「断刀门刀谱」以「断刀」为前缀，前缀规则会把刀谱错误吞并进断刀——基底名**相等**是唯一无歧义的变体判据。无括号的状态嵌入名（如段 1 截断形态的「断刀已彻底碎裂」）不享受基底名归一，依赖正文回查 + 多 token 共现兜底（172c.p 已覆盖）；段 2 实跑显示 LLM 的状态描述**均在括号内**（「断刀（裂纹上百道…）」），两级匹配已覆盖主流形态。

**短名保护**：基底名 len < 2 的条目（如「刀」）不参与基底名匹配，从根上挡住「刀」吞并一切刀类物品。

### 3.2 写入层：非物品碎片过滤（`_apply.py`）

拆单物品后、匹配前过滤：**基底名 len > 10 的条目拒绝登记**（写 warning 日志）。

依据：段 1+段 2 全部正常物品基底名 ≤ 8 字（「密室三把钥匙之一」8 字为最长相宜样本）；两个长垃圾碎片基底名分别为 13/13 字。长状态描述由括号承载（括号内容不限长），基底名 >10 字在 wuxia 数据里无一例外是叙述句碎片。

**短动词从句碎片**（≤10 字，如「捏碎第三枚铁片」）不在本次过滤范围内——形态复杂、与合法名词短语边界模糊（如「半阙刀谱记忆」），需段 3 数据进一步验证后再决定是否追加规则（§6）。

### 3.3 写入层：消耗状态流转（`_apply.py` + repo）

- **消耗标记**：条目匹配 `(已服下|已交出|已损毁|已用完|已耗尽|被夺走|被抢|抢走|已赠|已消耗|已捏碎|已碎裂|已折断)` 时（初始列表，按段 2/段 3 实跑新形态可扩充）：
  - 新条目 → create 时 `status='consumed'`（repo `create` 增加 status 参数，默认 held）
  - 命中已有 held 记录 → 除刷新 `last_used` 外，同步 `status='consumed'`（repo 增加 `update_status`）
- consumed/lost 记录永不被 `_find_forgotten_items` 计 forgotten（既有逻辑已跳过非 held，无需改）

写入时正文落地校验（密函型覆盖）**不纳入本任务**——settlement 的 source_quote 纪律涉及结算契约，单独立项评估；本任务 §3.2 的碎片过滤已覆盖其最恶劣形态。

### 3.4 wuxia live DB 存量修复

扩展 `.tmp/repair_172cp_inventory.py`（或新脚本 `.tmp/repair_172cq_inventory.py`），先备份 `.tmp/task172b_wuxia_ch100.pre172cq.db`：

2. 基底名 >10 字的记录直接删除（§3.2 同规则）
3. 含消耗标记的记录改写 `status='consumed'`
