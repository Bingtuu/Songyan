## 1. 现象

172c 段 3 边界复核暴露两个相互关联的设计缺陷：

1. **伏笔 resolve 机制完全失效**：wuxia 75 章、xuanhuan 100 章的 `foreshadowings.status='resolved'` 数量均为 **0**。每章平均埋 3-4 个伏笔（段 3 日志 `settlement.foreshadowing_planted` 事件 93 次），但 `settlement.foreshadowing_resolved` 事件 0 次。伏笔只埋不收，overdue 随章数线性堆积。
2. **continuity health 与 vdim overdue 门严重割裂**：vdim 口径统计 overdue=203，但 continuity health 仍有 5.6——health 公式看不到绝大多数 overdue，指标失真。

DB 现状（2026-07-16 实测）：

| DB | planted/active | due/active | overdue/active | overdue/dormant | overdue/archived | resolved |
|---|---:|---:|---:|---:|---:|---:|
| wuxia Ch75 | 40 | 3 | 20 | 36 | 153 | **0** |
| xuanhuan Ch100 | 129 | 3 | 14 | 36 | 121 | **0** |

关键判断：`foreshadowing_horizon_floor`（172a.p/172b.p）只是把逾期时间**推后**，不减少未回收伏笔总量——xuanhuan 靠 floor=48 压线 166≤168 是侥幸，不是机制健康。wuxia 段 3 证明 floor=12 在 resolve 失效时长窗口必然失控。**本任务修 resolve 根因，floor 是否调整留到 §7 按修复后实测决定。**

## 2. 根因（代码诊断已完成，2026-07-17）

### 2.1 缺陷一：resolve 失效是生成契约层缺陷，代码应用链路完整

代码侧 parse → validate → apply 端到端存在且正确：

- 解析：`_build_foreshadowing_update`（`src/songyan/agents/settlement_extractor/__init__.py:405`）接受 `operation in ("plant","resolve","update_status")`
- 应用：`apply_settlement`（`src/songyan/agents/settlement_extractor/_apply.py:681`）对 `resolve` + 非空 `foreshadowing_id` 执行 `foreshadowing_repo.update_status(id, "resolved")`，后续 `archive_resolved` 正常归档

失效发生在**生成契约层**，三个叠加因素：

**A. prompt 从未演示 resolve 形状**（主因）。`prompts/cards/settlement_extractor/1.0.3.yaml` 的 `foreshadowing_updates` JSON 示例只有 `plant`；规则 6 只说「新埋下或回收的伏笔」，但未说明回收必须输出 `operation="resolve"` + 从活跃伏笔列表取 `foreshadowing_id`。

**B. `resolved_hooks` 自由文本字段成为替代出口**。LLM 有收束信号可写时倾向写 `resolved_hooks`（prompt 有其示例），但该字段只被 `_thread_economy.py:36` / `_input_side_governance.py:37` 当叙事收束信号消费，**从不回写 `foreshadowings.status`**。

**C. overdue 伏笔从 settlement prompt 事实源中消失**。`_load_current_foreshadowings`（`__init__.py:83`）用 `ForeshadowingRepository.list_active()`，其 SQL 过滤 `lifecycle_status='active' AND status IN ('planted','due')`（`src/songyan/db/settlement_repo.py:106`）→ 伏笔一旦被 `mark_overdue` 翻转为 `overdue`，LLM 在后续章节再也看不到它，**resolve 窗口被压缩到「plant → overdue 翻转」之间**，窗口外永久不可回收。

另有两个**静默丢弃点**掩盖了失效（无日志，实跑无法分辨「LLM 没生成」与「生成后被丢」）：

- `_build_foreshadowing_update`：未知 operation → `return None`，无日志（`__init__.py:410`）
- `apply_settlement`：`resolve` 缺 `foreshadowing_id` → 无 else 分支，静默跳过（`_apply.py:681`）

**D. 同事务覆写：resolve 被 5.3 自动状态机当场翻回 overdue**（2026-07-17 TDD RED 阶段端到端测试抓获，任务书初稿未含）。`_update_continuity_tracking` 的 5.3 块（`_apply.py:1134`）对活跃伏笔做 `planted → due → overdue` 自动推进，但其 `list_active()` **走独立连接**，读不到事务连接上尚未提交的 resolve（陈旧读）→ 同章刚 resolve 的逾期伏笔被 `update_status(id, "overdue")` 静默翻回。实跑日志实证：`settlement.foreshadowing_resolved` 事件后紧跟同一 id 的第二次 `update_status`。这意味着**即使 LLM 正确生成 resolve、应用路径正确执行，回收也会在同事务内被抵消**——是 resolve 失效的第四层根因。

### 2.2 缺陷二：health 漏计 overdue 的范围比段 3 记录更广

`_find_overdue_foreshadowings`（`src/songyan/agents/continuity_auditor/_scanners.py:351`）复用 `list_active()`，同一 SQL 过滤导致**三层漏计**：

| 漏计层 | wuxia Ch75 实例数 |
|---|---:|
| lifecycle=archived 的 overdue | 153 |
| lifecycle=dormant 的 overdue | 36 |
| **lifecycle=active 但 status='overdue'**（被 `status IN ('planted','due')` 过滤） | 20 |

health 实际只统计到 status='due' 且过期的零星条目，与 vdim 冻结口径（`expected_resolve_chapter < up_to AND status != 'resolved'`，**无 lifecycle 过滤**，`.tmp/vdim_compare.py:177-181`）完全脱节。

**附带发现**：`get_unresolved_ratio`（`settlement_repo.py:307`）同样只算 `planted + due` → `foreshadowing_pressure` 信号同口径低估，需在本任务一并审计决策。

## 3. 修复范围

### 3.1 resolve 生成契约修复（缺陷一 A/B/C）

1. **prompt card 1.0.4**（`prompts/cards/settlement_extractor/1.0.4.yaml`，版本化新增，不改 1.0.3）：
   - `foreshadowing_updates` JSON 示例增加一条 `resolve` 样例（含 `foreshadowing_id` 取自活跃伏笔列表）；
   - 规则 6 拆为两条：plant 规则不变；新增 resolve 规则——「本章正文明确回收了活跃伏笔列表中的伏笔时，必须输出 `operation="resolve"` + 对应 `foreshadowing_id`」；
   - 澄清 `resolved_hooks` 仅是叙事收束摘要，**不能替代** `foreshadowing_updates` 的 resolve 操作。
2. **settlement prompt 事实源纳入口径修正**：`_load_current_foreshadowings` 改为纳入 overdue（复用 `list_schedulable()` 或新增 repo 方法），使 overdue 伏笔持续对 LLM 可见可 resolve；不改 `list_active()` 既有语义（其他消费者依赖）。
3. **两个静默丢弃点补 structlog 警告日志**：未知 operation 丢弃、resolve 缺 `foreshadowing_id` 跳过，各加一条 warning（含 project_id / chapter_number / 原始 operation 值）。
4. **validate 增加 resolve 防幻觉校验**：resolve 的 `foreshadowing_id` 必须存在于当前可 resolve 集合（含 overdue），否则丢弃该条并记 warning——不阻塞整单 settlement（与 plant 的容错级别一致）。
5. **5.3 同事务覆写修复（缺陷一 D，实施期新增）**：`_update_continuity_tracking` 的 5.3 自动状态推进跳过本单结算中刚 resolve 的伏笔 id（以 settlement 内容为准，绕开 `list_active()` 独立连接的陈旧读）。

### 3.2 health 口径修复（缺陷二）

6. `_find_overdue_foreshadowings` 改用与 vdim 冻结口径一致的查询：`expected_resolve_chapter < up_to AND status != 'resolved'`，不限 lifecycle、不限 status 白名单。在 `ForeshadowingRepository` 新增专用查询方法（如 `list_overdue_unresolved`），**不改 `list_active()` / `list_schedulable()` 既有语义**。
7. 审计 `get_unresolved_ratio` / `foreshadowing_pressure` 口径：记录决策（同改或保留并写明理由），结论入 DONE 文档。

### 3.3 明确不做

- 不提高任何体裁的 `foreshadowing_horizon_floor`（floor 是否调整由 §7 决策点按修复后实测决定）；
- 不改五门判定阈值、不改 `vdim_compare.py`、不改 sci-fi Ch1-100 冻结基线；
- 不做 `resolved_hooks` 自由文本 → DB 的模糊匹配自动 resolve（幻觉风险高，超出 MVP）；
- 不改 `mark_overdue` / `archive_overdue` / `archive_resolved` 的生命周期流转逻辑；
- 不处理 CED 门 FAIL（172c 段 3 第三项 FAIL，按 172c 任务书 §4 风险 2 路由，若修复后终段仍超线再立项 `172c.s`）。
