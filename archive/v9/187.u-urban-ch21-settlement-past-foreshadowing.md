## 根因判断

现有 `_validate_settlement()` 对 `ForeshadowingUpdate(operation="plant")` 的规则：

- `expected_resolve_chapter == current_chapter`：自动回填为 `current_chapter + 1`
- `expected_resolve_chapter < current_chapter`：硬错误，整章 settlement 进入 `needs_human_review`

这个规则能防止“新伏笔写入过去回收章”污染 DB，但 Ch21 暴露了一个运行时问题：LLM 会把已经发生/过期的线索误分类为新的 `plant` 伏笔，并给出过去章节作为 expected。此类条目本身不应写库，但它们也不应让正文 accepted 失败。

判断：

- 这是 settlement 抽取噪声，不是正文质量失败。
- 保持 DB 洁净的正确动作是**过滤无效 past-horizon plant**，而不是把它写入 DB，也不是放宽五门或 completion 口径。
- 真正硬错误仍应阻断：缺 `source_version_id`、source quote 无证据、数值公式不闭合、非法 setting key 等。

## 修复目标

1. 对 `operation="plant"` 且 `expected_resolve_chapter < chapter_number` 的 foreshadowing update：
   - 从 `settlement.foreshadowing_updates` 中剔除；
   - 记录 warning，例如 `settlement.foreshadowing_past_expected_filtered`；
   - 不追加 validation error。
2. 保留 `expected_resolve_chapter == chapter_number` 的现有回填行为。
3. 保留缺 `source_version_id` 的硬错误：没有来源版本的伏笔仍不得写入。
4. 保留 resolve 防幻觉校验：unknown/missing resolve id 仍过滤，不阻断。
5. 修复后必须 clean rerun Ch21：诊断 DB 不作为终判样本。

## 设计 review 要点

需要 review 的关键问题：

- 是否破坏 Task 121e 的原始安全意图？
  - 不破坏。过去 expected 的 plant 仍不写入 DB，只是从“硬失败”改为“过滤无效更新”。
- 是否可能掩盖 overdue 墙？
  - 不会。过滤的是“新 plant 写入过去 expected”的无效结算输出；已有 active/due/overdue 伏笔仍由 `ForeshadowingRepository` 与五门 overdue 统计处理。
- 是否降低事实源可信度？
  - 不降低。过滤后无效伏笔不进入事实源；其余 settlement 仍按原规则验证。
- 是否需要修改五门？
  - 不需要。completion 失败通过 clean rerun 解决，五门冻结口径不变。

### Review 结论（2026-07-20）

**准入开发**，但实现必须满足一个顺序约束：

- 先校验 `source_version_id` 是否存在；
- 再过滤 `expected_resolve_chapter < chapter_number` 的 past-horizon plant。

理由：past-horizon plant 可以作为 LLM 抽取噪声过滤掉，但缺 `source_version_id` 仍是事实链断裂，不能被过滤逻辑绕过。

现有 `tests/test_settlement_extractor.py::test_foreshadowing_past_expected_still_fails` 需要按新口径改为过滤测试；`test_foreshadowing_empty_version_id` 与 `test_foreshadowing_current_chapter_expected_backfilled` 必须保持原语义。
