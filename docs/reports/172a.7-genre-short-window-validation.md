## 未达标项 → 172a.p（已修复，验收中）

**overdue foreshadowing = 28（目标 < 5）**：这是 V8 验收 S 维度，floor=0（旧行为）下**未通过**。

根因（真实 run DB 解剖，非推断）：
- xuanhuan 每章密集埋设伏笔，`expected_resolve_chapter` 由 LLM 在结算时选定，horizon 偏短（峰值 +2/+4/+6）。
- 关键对照：**scifi 与 xuanhuan 短窗口 resolved 均为 0**——overdue 差异不是回收率，而是 **plant-time horizon 长度**（scifi 中位 12-13 故 overdue≈0/1；xuanhuan 近端故 overdue=28）。
- overdue 计数逻辑（`_scanners._find_overdue_foreshadowings`）= `expected_resolve_chapter < 当前章 且 status != resolved`，与本报告度量一致，28 是真实值。

**纠错**：初稿曾断言"运行时参数化无法压下 overdue"——该结论**仅对 `foreshadowing_evaporation`**（172a.6 注入排序加权）成立。但**plant-time horizon 夹紧同属运行时参数**（新增 `GenreRuntimeProfile.foreshadowing_horizon_floor`），不改结算 prompt、不新增节点，实跑 DB 模拟证明有效：

```
xuanhuan uco3ialu DB 若 plant 时夹到 >= planted+floor：
  floor=10 -> overdue 28->6    floor=12 -> overdue 28->1
```

**已实现（172a.p，commit 7734716）**：xuanhuan floor=12，scifi floor=0（零回退）。floor=12 验收 run 在线确证：Ch1-4 伏笔 horizon 硬底=12，无一低于 12。最终 Ch15 overdue 待该 run 完成确认。
