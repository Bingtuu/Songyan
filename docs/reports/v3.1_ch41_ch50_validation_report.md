# Songyan V3.1 Ch41-Ch50 真实 LLM 验证测试报告

> **报告日期**: 2026-06-07  
> **测试范围**: Ch41-Ch50（scifi + webnovel_intense）  
> **测试方式**: 真实 DeepSeek API 调用，`auto_confirm=True`  
> **测试目标**: 验证 V3.1  layered summary + context pruning 设计能否支撑长尺度（100-300章）稳定生成

---

## 1. 执行摘要

本次测试是 Songyan V3.1 阶段首次针对 **Ch41-Ch50 高章节段** 进行的真实 LLM 端到端验证。测试暴露出当前架构在 **长尺度上下文管理** 上的根本性缺陷，虽然在 Layer 1 / Layer 2 紧急修复后成功跑通了 Ch41-Ch50，但多项核心指标已接近或超出设计边界。

**核心结论**:  
> **当前设计在简单修复后可以通过 50 章验证，但无法稳定支撑 100 章，更无法支撑 300 章。** 必须对上下文架构进行结构性改造（或接受显著的质量/成本妥协），否则到 Ch70-Ch100 阶段将面临系统性崩溃。

## 4. 发现的问题与严重性分级

### 🔴 P0 — 阻塞级（已导致或必将导致失败）

#### 4.1.1 上下文 Token 预算不可恢复地超支

**现象**:  
`budget_used` 从 Ch43 的 1.58 增长到 Ch50 的 2.00，且 `current_tokens` 从 17715 膨胀到 32139。即使 BudgetPruner 将所有可裁剪分区（soft_refs, open_threads, foreshadowing, recent_plot, character_states）全部压缩，`final_tokens` 仍超预算 90-110%。

**根因**:  
不可裁剪分区（hard_constraints + genre_rules + mode_rules + arc_context + volume_context + human_marks + dialogue_style_cards + setting_snapshots 基线）已膨胀到 **~18000 tokens**，超过 9600 的动态预算。

**对 100 章的影响**:  
按当前趋势（每 10 章 `current_tokens` 增长约 4000-5000），到 Ch70 时 `current_tokens` 将达 **45000+**，`final_tokens` 将达 **25000+**，`budget_used` 将达 **2.6+**。Writer 将几乎没有可用 token 生成正文，导致：
- 字数进一步失控
- scene 结构崩溃
- 响应时间指数增长
- 最终超时或生成不可用内容

**评级**: 🔴 **P0 — 100 章前必将阻塞**

---

#### 4.1.2 字数目标控制完全失效

**现象**:  
从 Ch45 起，实际字数稳定在目标的 **160-220%**。RuleAuditor 持续报 `word_count_ok=False`，但 RevisionHandler 无法有效修复（只修局部问题，不改整体长度）。

**根因**:  
Writer Prompt 中缺少强制的字数约束执行机制。`word_count_target=3200` 只是建议性参数，LLM 在复杂上下文下倾向于"多写"以确保覆盖所有约束。

**对 100 章的影响**:  
若每章实际 6000-7000 字，100 章总字数将达 **60-70 万字**，远超网文正常节奏。RAG 索引、chunk 数量、摘要生成都将线性恶化。

**评级**: 🔴 **P0 — 质量不可接受**

---

#### 4.1.3 RevisionHandler 系统性失效

**现象**:  
- `content_truncated`: LLM 返回的修订内容被截断到 23-27%，只能 revert
- `patch_not_found`: 原文定位失败
- `patch_collision_skipped`: 多个 patch 冲突
- `partial_patches`: 大量 issue 无法应用
- `revision_rebound`: 修订后问题反而增加（Ch42: 7→17 issues；Ch46: 9→16 issues）

**根因**:  
RevisionHandler 基于文本匹配做 patch，在上下文极大、LLM 输出不稳定时，匹配精度断崖式下降。

**对 100 章的影响**:  
自动修订是闭环的核心。RevisionHandler 失效意味着每章都需要人工介入，或者接受低质量输出。

**评级**: 🔴 **P0 — 自动闭环不可持续**

---

### 🟡 P1 — 严重级（显著影响质量和成本）

#### 4.2.1 ContinuityAuditor 约束爆炸

**现象**:  
- Ch42: score=0, overdue=9
- Ch45: score=0, overdue=25
- Ch48: score=0, **orphaned=27, overdue=41, constraints_written=236**

**对 100 章的影响**:  
到 Ch100 时，human_marks 可能累积到 **150+**，setting_snapshots 到 **200+**。即使 ContextManager 只取前 10 个，过滤和排序成本也会增加。更关键的是，大量未回收伏笔会让故事逻辑陷入"补丁堆补丁"状态。

**评级**: 🟡 **P1 — 长期累积风险**

## 5. 根因分析：为什么当前设计无法支撑 100 章

### 5.1 核心设计矛盾：所有历史都在 context 里

当前架构的假设是：**通过分层摘要（Arc/Volume）减少历史细节，但保留所有元数据（setting_snapshots, foreshadowings, human_marks, character_states）**。这导致：

- 精细摘要可以被截断 ✅
- 但元数据表只增不减 ❌
- 这些元数据最终都进入 hard_constraints / soft_refs ❌

**结果是：无论 summary 多么精简，context 的"地板"在不断抬高。**

### 5.2 关键量化分析

假设当前趋势不变（每章新增 ~2 个 setting_snapshots、~1 个 foreshadowing、~0.5 个 human_mark）：

| 章节 | setting_snapshots | foreshadowings | human_marks | 预估 static baseline* |
|------|-------------------|----------------|-------------|----------------------|
| Ch50 | 84 | 49 | 73 | ~18000 tokens |
| Ch75 | ~134 | ~74 | ~110 | ~24000 tokens |
| Ch100 | ~184 | ~99 | ~145 | ~30000 tokens |

`* static baseline = hard_constraints + genre_rules + mode_rules + arc_context + volume_context + human_marks + soft_refs 的不可压缩部分`

当 static baseline 超过预算（Ch75 时 baseline ≈ 24000 > 9600），BudgetPruner 将完全失效。

### 5.3 修复的边际收益递减

Layer 2 修复（截断 summary、过滤 dialogue cards、限制 marks）本质是**在现有架构内做裁剪**。但这些修复的边际收益很低：

- `previous_summary`: 244 → 123 chars（-121 tokens）
- `recent_plot`: 每章摘要 -200 tokens
- `dialogue_style_cards`: 可能 -500 tokens
- `human_marks`: 每章限制写入 28 条（但 DB 仍累积）

这些优化只能延缓崩溃，**无法改变"静态基线持续增长"的根本趋势**。

## 6. 距离 100 章里程碑的差距评估

### 6.1 当前位置

我们已经证明：**在紧急修复后，Ch50 可以跑通。** 但这是"带着氧气瓶登顶 5000 米"，不是可持续的常规能力。

### 6.2 到 100 章还需要什么

| 维度 | 当前状态 | 100 章要求 | 差距 |
|------|---------|-----------|------|
| **上下文预算** | budget_used≈2.0 | <1.5（建议） | 需要结构性改造 |
| **字数控制** | 实际 200-220% 目标 | ±20% | 需要 Writer 级强制约束 |
| **Revision 成功率** | ~60% patches 应用 | >90% | 需要重写 Revision 策略 |
| **Continuity 健康度** | score=0 | >7 | 需要伏笔回收机制 |
| **单章耗时** | 6-10 分钟 | <5 分钟 | 需要更小上下文或更快模型 |
| **人工介入率** | 0%（auto_confirm） | <5% | 需要自动闭环真正可用 |

### 6.3 结论：100 章可行性

**三种情景分析**:

#### 情景 A：只做类似 Layer 2 的渐进式修复（当前路径）
- **可行性**: 可能跑到 Ch60-Ch70
- **Ch100 可能性**: <20%
- **代价**: 每章耗时翻倍，质量持续下降，需要频繁人工介入

#### 情景 B：结构性改造上下文架构
- **改造点**:
  1. 引入**分层设定库**：setting_snapshots 按 arc/volume 聚合，不再全量加载
  2. 引入**伏笔生命周期管理**：自动归档/回收旧 foreshadowing，不再全量激活
  3. 引入**角色出场窗口**：只加载当前 arc 内出场的角色
  4. 将 genre_rules / mode_rules 按 chapter_type 动态裁剪
  5. Writer 输出强制截断到目标字数 ±10%
- **可行性**: 可以跑到 Ch100
- **Ch100 可能性**: >80%
- **代价**: 2-3 周的架构改造

#### 情景 C：颠覆式改造（Agent 记忆 + 检索增强规划）
- **改造点**:
  1. ContextManager 不再组装完整包，而是按需检索
  2. GoalPlanner 自己决定需要查什么
  3. Writer 分段生成，每段只依赖局部上下文
- **可行性**: 可以跑到 Ch300
- **Ch100 可能性**: >95%
- **代价**: 1-2 个月的重构

## 7. 建议

### 7.1 短期（1-2 周）：完成 V3.1 最小可用

1. **跑通 Ch2-Ch50 端到端**
   - 用当前 Layer 2 修复后的代码，从 Ch2 开始跑一次完整验证
   - 确认 Ch30-Ch50 没有回归

2. **修复 RevisionHandler 的核心 bug**
   - `content_truncated` 问题：增大 RevisionHandler 的 max_tokens 或分段 revision
   - `patch_not_found` 问题：改进 fuzzy match 策略

3. **Writer 强制字数截断**
   - 在 Writer 输出后，若字数超过目标 130%，直接截断到最近 scene 边界

### 7.2 中期（2-4 周）：为 100 章做结构性改造

1. **分层 setting 库**
   - setting_snapshots 不再全量进入 soft_refs
   - 按相关性（最近提及章节 + 当前 chapter goal 关键词）检索 Top-10

2. **伏笔生命周期管理**
   - foreshadowing 超过预期回收章节 20% 后自动归档
   - 只保留 `due/overdue` 和最近 5 章 planted 的伏笔

3. **角色出场窗口**
   - 只加载"当前 arc 内出场过的角色" + protagonist
   - 角色状态也按时间窗口过滤

4. **Genre/Mode 规则动态裁剪**
   - 按 chapter_type 只加载相关规则

### 7.3 长期（1-2 个月）：为 300 章做架构升级

1. **从"组装完整上下文"转向"按需检索上下文"**
2. **引入 Agent 记忆层**：每个 Agent 有自己的记忆索引
3. **分层生成**：先写大纲 → 再写 scene → 再写段落，每步只依赖局部上下文

## 9. 最终结论

> **Songyan V3.1 当前设计可以跑到 50 章，但无法稳定支撑 100 章。**
>
> 我们已经验证了两个关键假设：
> 1. **Layer 1 修复有效**: Writer scene 检查放宽解决了阻塞问题。
> 2. **Layer 2 修复有效**: 上下文裁剪延缓了 budget_used 的恶化。
>
> 但这些修复是**止痛药，不是根治方案**。到 Ch70-Ch100 阶段，上下文静态基线的持续增长将使 BudgetPruner 完全失效，Writer 将没有足够 token 生成合格正文。
>
> **若 100 章是 V3.1 的 hard milestone，必须在 4 周内启动上下文架构的结构性改造。**
