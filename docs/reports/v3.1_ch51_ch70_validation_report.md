本次验证在 076-080 修复后运行了 Ch52-Ch70 共 **19 章**（Ch51 缺失）。核心发现：

**结论**：076-080 的修复将"稳定运行区间"从 Ch50 延长到 **Ch60 左右**，但无法支撑到 Ch70。要在 Ch70 维持 budget_used < 1.5，需要更深层的上下文架构改造。

## 6. 根因分析

### 6.1 为什么 budget_used 在 Ch60 后再次恶化

Ch41-Ch50 验证报告中已经指出：
> "静态基线（hard_constraints + genre_rules + mode_rules + arc_context + volume_context + human_marks + soft_refs）持续增长"

076-080 的修复（字数截断、Setting 库排序、BudgetPruner 硬断言、伏笔生命周期、分段修订、Arc 角色窗口）延缓了崩溃，但**没有改变"元数据表只增不减"的根本趋势**。

量化验证：
- Ch50 时 setting_snapshots=84, foreshadowings=49, human_marks=73
- Ch70 时 setting_snapshots≈129, foreshadowings≈62, human_marks 持续增长

### 6.2 为什么字数控制仍不达标

1. **Writer Prompt 中字数约束仍是建议性**：LLM 在复杂上下文下倾向于"多写"
2. **Revision 阶段增加字数**：截断后的 draft 在 revision 中可能被扩充（如 Ch56 draft 3731 → accepted 5797）
3. **截断阈值 1.5x 太宽**：允许多章在 4000-5000 字区间不触发截断

## 7. 建议

### 7.1 短期（若必须跑到 Ch70）

1. **降低字数截断阈值到 1.2x**（但可能增加截断触发率）
2. **RevisionHandler 增加字数上限检查**：revision 后若字数 >1.4x target，拒绝该 revision
3. **动态预算**：Ch60 后将预算从 8000 提升到 12000

### 7.2 中期（支撑 100 章）

1. **setting_snapshots 生命周期管理**：超过 N 章未提及的 setting 自动归档
2. **human_marks 强制回收**：resolved_at 不为空的 marks 不再加载
3. **foreshadowing 自动回收**：resolved 的伏笔立即从 context 中移除
4. **Arc/Volume 摘要进一步压缩**：当前 ArcSummary 仍过长

### 7.3 长期（支撑 300 章）

1. **从"组装完整包"转向"按需检索"**：ContextManager 不再预加载所有数据
2. **分层生成**：先写大纲 → 再写 scene → 再写段落
