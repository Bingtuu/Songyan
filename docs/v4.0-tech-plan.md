## 1. 执行摘要

### 1.1 为什么要 V4.0

Songyan V3.x 验证了以下假设：

> **"通过 BudgetPruner 硬断言 + 分层摘要 + 元数据裁剪，可以支撑 100 章网文生成。"**

**Task 081 验证结果否定了这个假设。**

Ch52-Ch70 真实 LLM 验证数据显示：

- budget_used 从 0.88 升至 **2.32**（Ch70），Ch60 后持续恶化
- 平均字数 4062（目标 3200），仅 **42%** 达标
- 连续性健康分持续 **2.0**（远低于 5.0 目标）

**根因诊断**：V3.x 架构存在三个独立但相互叠加的问题：

| 问题 | 具体表现 | 严重程度 |
|------|---------|---------|
| **元数据只增不减** | setting_snapshots Ch70=129 条，foreshadowings 62 条，human_marks 100+，BudgetPruner 裁不动 | 无需架构改造即可修复 |
| **字数控制过松** | Writer prompt 中 word_count_target 仅建议性，截断阈值 1.5x 太宽，RevisionHandler 无字数约束 | 不需要改动 Agent 行为 |
| **静态基线超预算** | genre_rules + mode_rules + hard_constraints + arc/volume = ~18K tokens @ Ch70，超过 8K 预算 | 需要更长远的架构方案 |

### 1.2 本版计划的核心变化（对比 V4.0-TECH-PLAN-001）

上一版计划的核心决策是 **"废弃 ContextPackage，全量重写为 ContextService 架构"**。Review 后调整为：

| 变化 | V4.0-TECH-PLAN-001 | V4.0-TECH-PLAN-002（本版） |
|------|-------------------|--------------------------|
| 策略 | 一次性架构重写 | 增量修补、门控决策与可选演进 |
| Phase A | ContextService 基建 | **数据生命周期管理 + 动态预算（不改架构）** |
| Phase B | Agent 改造 + Prompt 重写 | **Agent 约束硬化（不改 Prompt）** |
| Phase C | 工作流改造 | **ContextService 演进（可选，有门控）** |
| 风险 | 高风险，9 周工期 | 中低风险，6 周核心，门控后决定是否多花 3 周 |

**核心原则：能用参数和约束解决的问题，不动架构；能用生命周期管理控制的数据，不改 Agent。**

### 1.3 V4.0 核心目标（修订）

| 维度 | V3.1 基线 (Ch70) | Phase A+B 目标 (Ch100) | Phase C 目标 (Ch100, 若需) |
|------|------------------|----------------------|--------------------------|
| budget_used | 2.32 | **< 1.6** | **< 1.3** |
| 字数达标率 (+/-20%) | 42% | **> 65%** | **> 75%** |
| 连续性健康分 | 2.0 | **>= 3.5** | **>= 4.5** |
| 单章耗时 | 5-6 min | **< 4 min** | **< 3.5 min** |
| 流程跑通率 | 100% | **100%** | **100%** |

Phase A+B 的目标设定考虑了"不动架构能解决的问题上限"。如果数据表明能达到或超过这些目标，Phase C 可以跳过或推迟到 V4.1。

## 2. 现状分析与行业定位

### 2.1 V3.x 架构

Songyan 当前架构：

```
Phase1Graph ---> ContextManager ---> ContextPackage
                                            |
               |-----------------------------|----------------|
               v                             v                v
          RuleAuditor                      Writer        LLMAuditor
          (规则检测+定位)                (初稿生成)       (语义审查+证据)
                                                             |
                                                       RevisionHandler
                                                       (证据驱动修订)
                                                             |
                                                       SettlementExtractor
                                                       (状态结算+验证)
```

**问题**：ContextManager 从 DB 加载全量数据，组装成 ContextPackage 后广播给所有 Agent。当数据表只增不减时，ContextPackage 体积线性增长，而 BudgetPruner 只能做边际裁剪——静态基线（genre_rules + mode_rules + hard_constraints 约 ~18K tokens @ Ch70）永不缩小。

### 2.2 数据膨胀量化

| 元数据表 | Ch30 | Ch50 | Ch70 | 年增长率 |
|----------|------|------|------|---------|
| setting_snapshots | 40 | 84 | 129 | +~2/章 |
| foreshadowings (active) | 15 | 49 | 62 | +~1/章 |
| human_marks (unresolved) | 20 | 73 | 100+ | +~1.5/章 |
| character_states | 80 | 183 | 200+ | +~2/章 |

**Ch70 上下文详情**：
- current_tokens=25288（预算 8K 的 3.16 倍）
- final_tokens=18593（六步硬断言裁剪后，仍为预算的 2.32 倍）
- 6 步裁剪共裁掉 ~6695 tokens，但静态基线不变

### 2.3 Songyan 在行业中的位置

> 详细分析见 `docs/ai_writing_research_report.md`。

2026 年主流 AI 小说生成开源项目的能力分布：

| 项目 | 类型 | 最长验证长度 | 一致性保障机制 | 工程成熟度 |
|------|------|------------|--------------|----------|
| **InkOS** | 商业（文档公开） | 未公开 | 33 维审计，多 Agent 管线 | 高 |
| **RecurrentGPT** | 学术 PoC | 理论无限 | LSTM 模拟记忆 + RAG 回溯 | 低（无测试、无类型） |
| **fiction-forge** | 工具链 | 286K 词（人工） | MCP 注入 + 散文扫描 | 中（无测试） |
| **SuperWriter** | 学术研究 | 论文环境 | Plan-Write-Refine + MCTS-DPO | 中（学术代码） |
| **LongWriter** | 学术研究 | 10K+ 词/次 | 依赖模型自身能力 | 中（SFT 管线） |
| **wordplay** | 桌面工具 | 长篇小说 | 角色/伏笔手动追踪 | 中高 |
| **snowmeth** | 全栈应用 | 完整小说 | 雪花方法 + 顺序依赖 | 中高 |
| **Songyan V3.x** | **开源管线** | **Ch70 (已验证)** | **13 Agent + 双审计 + Settlement 验证** | **高** |

**Songyan 的独特定位**：

1. **证据链驱动的修订闭环**：LLMAuditor 要求 critical/major issue 必须有 evidence_quote，RevisionHandler 只做 patch 不重写——这是现有开源项目中唯一的设计
2. **Agent 职责刚性边界**：13 个 Agent 各自"能做什么、不能做什么"被明确定义，包括 LiteraryAuditor 不阻塞 accept、CreativeDirector 不新增硬剧情事件
3. **Settlement 驱动的状态追踪**：每章 accept 后自动结算，验证 character_states old_value 必须与 DB 一致、source_quote 必须在正文中存在
4. **1430+ 测试覆盖**：远超同类项目（RecurrentGPT 无测试，fiction-forge 无测试）

**V3.x 已验证的事实**：工程理念是对的，架构设计是合理的，但在"数据量增长到一定程度后预算控制失效"这一点上存在天花板。这个天花板大约在 **Ch60** 附近。

## 3. V4.0 策略选择

### 3.1 三个问题，三个不同级别的修复

| 问题 | 对应 Phase | 改动范围 | 预期收益 |
|------|-----------|---------|---------|
| 元数据只增不减 | Phase A：数据生命周期管理 | repository 层（无 Agent 改动） | setting -40%, foreshadowings -30%, human_marks -50% |
| 字数控制过松 | Phase B：Agent 约束硬化 | RevisionHandler + Writer 参数 | 字数达标率 42% -> 65%+ |
| 静态基线超预算 | Phase C：ContextService 演进（可选） | 新增 ContextService 层 | budget_used < 1.3 |

### 3.2 为什么选增量方案而非一次性重写

| 维度 | 一次性重写（原方案） | 增量修补 + 门控（本方案） |
|------|--------------------|------------------------|
| 风险暴露时间 | 4-6 周后才可见效 | Phase A 完成后即可验证（1 周） |
| 质量回退风险 | 高（Prompt 重写、Agent 行为改变） | 低（不改 Prompt、不改 Agent 行为） |
| 回滚代价 | 高（目录替换、配置开关） | 低（参数回退、功能开关） |
| 测试影响 | 大量测试需要更新 | 少量新增测试，1430 个现有测试不变 |

**决策原则**：每一次改动都应该可以被独立验证。如果一个改动需要等到 4 周后才能判断是否有效，那这个改动太大了。

### 3.3 Phase C 门控条件

Phase C（ContextService 演进）仅在以下条件**同时满足**时启动：

1. Phase A+B 完成后 Ch71-Ch90 验证显示 budget_used > 1.6
2. Phase A+B 完成后字数达标率 > 60% 但 < 75%
3. health_score 仍 < 3.5
4. 静态基线仍占据 > 40% 的 ContextPackage token 总量

如果 Phase A+B 的验证数据显示 budget_used < 1.5 且字数达标率 > 70%，则 Phase C 推迟到 V4.1。

## 4. Phase A：数据生命周期 + 动态预算（Quick Wins）

**预估工期**：2 周  
**改动范围**：repository 层 + BudgetPruner 公式  
**代码风险**：低（不修改任何 Agent 代码，不修改 workflow 节点）

### 4.1 数据生命周期管理

**统一策略**：所有元数据表遵循统一的生命周期策略，使用 status 标记代替软删除：

```
active ---> dormant ---> archived
  |            |            |
  | 超过       | 超过       | 不再进入
  | N 章       | M 章       | 上下文
  | 未提及     | 未提及     |
  +------------+------------+
```

**各表生命周期**：

| 表 | active -> dormant | dormant -> archived | 例外 |
|----|-----------------|-------------------|------|
| setting_snapshots | 最近 10 章内未提及 | 20 章未提及 | is_critical 永不休眠 |
| foreshadowings | overdue 超过 5 章 | resolved 或 overdue >15 章 | -- |
| human_marks | 最近 10 章未提及且 unresolved | 已 resolved 或 >20 章未提及 | priority >= 8 保留 |
| character_states | 最近 5 章未出场 | 15 章未出场 | protagonist 永不过期 |
| chapter_chunks (RAG) | 最近 20 章 | >40 章 | -- |

**生命周期调度器**：新增 LifecycleScheduler，每 5 章异步触发一次归档清理。不新增独立进程，在 SettlementExtractor 之后触发。

**BudgetPruner 使用生命周期字段**：以下分区变为有条件裁剪：

| 分区 | V3.x | V4.0 Phase A |
|------|------|-------------|
| chapter_goal | 永不裁剪 | 永不裁剪 |
| creative_brief | 永不裁剪 | 永不裁剪 |
| hard_constraints | 永不裁剪 | **仅裁 human_marks (dormant)** |
| genre_rules | 永不裁剪 | **按 current_chapter 分组加载** |
| mode_rules | 永不裁剪 | **按 current_chapter 分组加载** |

### 4.2 动态预算

**预算公式**：

```
dynamic_budget = 8000 + chapter_number * 80
  (Ch1: 8080, Ch50: 12000, Ch70: 13600, Ch100: 16000)
```

每章增加 80 tokens，与数据增长率（~2 setting + ~1 foreshadowing + ~2 character_states / 章）匹配。

**预期效果**：Ch70 时预算从 8000 -> 13600，配合生命周期管理将数据量降低 30-40%，预计 budget_used 从 2.32 回落到 1.3-1.6。

## 5. Phase B：Agent 约束硬化

**预估工期**：2 周  
**改动范围**：RevisionHandler + Writer 约束函数  
**代码风险**：中低（不修改任何 Agent 的 Prompt，不修改 workflow 节点签名）

### 5.1 RevisionHandler 字数上限

**问题**：Ch56 draft 3731 -> accepted 5797（+55%），RevisionHandler 无字数约束

**改动**：在 run_segmented_revision / run_patch_engine 返回后增加硬约束：
- 如果 revision 后字数 > target * 1.3，做 _enforce_word_count 二次截断
- 如果 revision 后字数 < target * 0.7，回退到原始 draft 内容

### 5.2 截断阈值收紧 + 全链路保护

**问题**：Writer 截断阈值 1.5x = 4800 字才触发，大量 4000-5000 字章节不被截断。

**改动**：截断阈值从 1.5x 收紧至 1.3x，下界保护 0.75x。增加 draft -> revision 全链路保护：revision 后若超上限，做二次截断。

### 5.3 动态预算纳入 ContextManager

在 ContextPackage 组装阶段使用动态预算公式，让 BudgetPruner 在不同章节有不同的硬限制。此改动在 ContextManager 内部，不修改 Agent 和 workflow 节点。

### 5.4 不做的事

| 不做 | 原因 |
|------|------|
| 不修改 Writer Prompt | V3.x Prompt（1.0.6）已经过多轮调优 |
| 不修改 Auditor Prompt | 审查质量依赖 Prompt 稳定性 |
| 不新增 Agent | V3.0 约束：不新增 Agent、Workflow 节点 |
| 不修改工作流节点签名 | Phase1Graph 节点函数签名保持不变 |

## 6. Phase C：ContextService 演进（可选，有门控）

**预估工期**：3 周  
**门控条件**：见第 3.3 节

### 6.1 解决的问题

Phase A+B 解决"数据太多 + 约束太松"但未解决"静态基线过大"——如果 Phase A+B 后 Ch100 的 budget_used 仍 > 1.6，需要启动 Phase C。

### 6.2 ContextService 设计

不废弃 ContextManager，在其之上增加 ContextService 作为可选包装：

```python
class ContextService:
    """按需检索服务 -- 可选层."""

    async def get_l0_meta(self, project_id: str) -> tuple[...]: ...
    async def get_l1_plot(self, project_id: str, chapter_number: int) -> tuple[...]: ...
    async def get_l2_characters(self, ...) -> list[...]: ...
    async def get_l2_settings(self, ...) -> list[...]: ...
    async def get_l2_foreshadowings(self, ...) -> list[...]: ...
    async def get_l2_human_marks(self, ...) -> list[...]: ...
```

### 6.3 Agent 上下文需求声明

```python
AGENT_CONTEXT_PROFILES = {
    "writer": {"layers": ["l0", "l1", "l2_c", "l2_s", "l2_f", "l2_m"]},
    "rule_auditor": {"layers": ["l0"]},
    "llm_auditor": {"layers": ["l0", "l1", "l2_c"]},
    "revision_handler": {"layers": ["l0", "l1", "l2_c", "l2_s"]},
    "settlement_extractor": {"layers": ["l0", "l1"]},
    "summary_writer": {"layers": ["l0", "l1"]},
}
```

### 6.4 不做的事

| 不做 | 原因 |
|------|------|
| 不修改 Agent Prompt | Prompt 内容不变，仅供应方式改变 |
| 不修改工作流节点签名 | context_package 保留为兼容字段 |
| 不废弃 ContextManager | 旧代码完整保留 |
| 不重写 Phase1Graph | 仅 gateway 函数判断走哪个路径 |

## 9. 风险与回滚

### 9.1 风险矩阵

| 风险 | 可能性 | 影响 | 缓解措施 |
|------|--------|------|---------|
| 生命周期归档误删需要的数据 | 低 | 中 | 软删除；protagonist/critical 永久保留 |
| Revision 字数上限截断合法修订 | 中 | 低 | 上限 1.3x，足够正常修订 |
| Phase C 引入回归 bug | 中 | 高 | USE_CONTEXT_SERVICE=False 回退 |
| 工期超支 | 中 | 中 | Phase A+B 可独立交付 |

### 9.2 回滚策略

| 变更 | 回滚方式 |
|------|---------|
| 生命周期管理 | ENABLE_LIFECYCLE_CLEANUP=False；或 UPDATE status='active' |
| 动态预算 | BUDGET_PRUNER_HARD_LIMIT=8000（V3.x 固定值） |
| Revision 字数上限 | 配置开关或回退代码 |
| ContextService | USE_CONTEXT_SERVICE=False，回到 ContextPackage 旧路径 |

### 9.3 自动回滚触发条件

- pytest 失败数 > 10：暂停推进
- 端到端验证有任何失败：暂停推进
