## 1. 问题（172a.7 实跑暴露）

xuanhuan `--end 15`（base=15000）实跑：**overdue foreshadowing = 28**，V8 验收 S 维度目标 `< 5`，**未通过**。这是 172a.7 唯一未达标的硬指标。

## 2. 根因（真实 run DB 证据，非推断）

对两个 xuanhuan 实跑 DB 与 scifi 实跑 DB 做伏笔生命周期解剖（脚本 `.tmp/analyze_foreshadowing.py`）：

| 体裁 | 窗口 | planted | resolved | horizon 分布 | overdue |
|---|---|---|---|---|---|
| scifi | Ch1-10 | 32 | **0** | 中位 12-13，长尾到 17；6 条 NULL | **1** |
| xuanhuan | Ch1-15 | 56 | **0** | 峰值 +2/+4/+6（短） | **28** |
| xuanhuan（另一次） | Ch1-15 | 50 | **0** | 同上偏短 | 40 |

**决定性发现**：

1. **resolved 全为 0** —— 短窗口内两个体裁都没有主动回收伏笔。所以 overdue 差异**不是**"xuanhuan 不回收、scifi 回收"造成的。
2. **真正差异是 plant 时的 horizon 长度**：scifi 的结算 LLM 把回收点推得很远（中位 12-13，很多 13-17），短窗口内自然"还没到期"；xuanhuan 的 LLM 给出近端 horizon（+2/+4/+6），planted 后很快越过当前章即判 overdue。
3. V8-README 里"baseline 13"是在 **Ch8 halt**（只埋了 7 章）时测的，与 Ch14/15（埋满）的 28 不同口径，部分是分母差异。

### 与 172a.6 evaporation 的关系（澄清一处早期误判）

172a.7 初稿曾断言"运行时参数化无法压下 overdue"。这个结论**只对 `foreshadowing_evaporation` 成立**——该 Profile 只影响 `_rank_foreshadowings` 的注入紧迫性加权（且当前尚未接线），既不改 plant horizon、也不改回收。

但"运行时参数化"不止 evaporation 一种：**在 plant 时按体裁夹紧 `expected_resolve_chapter` 的 horizon 下限**同样是纯运行时参数（GenreRuntimeProfile 字段），不改 prompt、不新增节点。模拟证明它有效：

```
xuanhuan uco3ialu 实跑 DB，若 plant 时把 horizon 夹到 >= planted+floor：
  floor=6  -> overdue 28 -> 17
  floor=8  -> overdue 28 -> 12
  floor=10 -> overdue 28 -> 6
  floor=12 -> overdue 28 -> 1   ✅（远低于目标 5）
```

## 3. 方案（MVP 边界内，scifi 零回退）

新增 `GenreRuntimeProfile.foreshadowing_horizon_floor: int = 0`：

- **语义**：plant 时把 `expected_resolve_chapter` 夹到 `>= planted_in_chapter + floor`，**只抬高、从不缩短**。
- **scifi = 0**：`floor <= 0` 时函数完全不改输入 → 旧行为逐字节不变（scifi horizon 天然长，也无需夹）。
- **xuanhuan = 12**：模拟 overdue 28→1。
- **wuxia / urban = 0**：默认回退（wuxia 短窗口伏笔密度未超标；后续按 172a.7 数据再定）。
- **None horizon 不夹**：LLM 未给 horizon（表示"未知"）时保持 None 语义。

### 落点

| 位置 | 改动 |
|---|---|
| `models/genre_runtime_profile.py` | 新增 `foreshadowing_horizon_floor` 字段（default 0, ge 0） |
| `db/genre_runtime_profile_repo.py` | xuanhuan registry 设 `foreshadowing_horizon_floor=12` |
| `agents/settlement_extractor/_apply.py` | 新增纯函数 `_clamp_foreshadowing_horizon(...)`；`apply_settlement` 增 `foreshadowing_horizon_floor=0` 参数；plant 分支调用夹紧 |
| `workflows/_nodes.py` | `accept_with_settlement_boundary` 按项目 genre 解析 `load_profile(...).foreshadowing_horizon_floor` 后传入 |

### 为什么在 MVP 边界内

- **纯运行时参数**：与 base_budget、focal_gaps 同类，只是多一个 profile 字段。
- **不改结算 prompt**：LLM 输出照旧，夹紧在写库前发生（validation 已过，且只抬高 horizon，不可能触发"expected < 当前章"的硬校验）。
- **不新增 Agent/节点**：复用既有 `apply_settlement` 写路径。
- **无 Profile 100% 回退**：`load_profile` 永不抛错，未知体裁 → scifi baseline → floor 0 → 旧行为。
