## 背景

193.r 评估遗留中仍作用于段边界审计路径的两项：

1. **192.aw 型 stale health 无防护**：continuity 审计每 3 章一次，five-gate health 取 `checked_up_to_chapter <= up_to` 的最新报告（`five_gate_acceptance.py:368-383`），段边界末章报告可能滞后——192.aw 实证：@200 读到 Ch198 的 health 7.6（实际补跑后 8.1）造成假 FAIL，靠人工补跑 continuity audit 才翻案。当前输出不含报告章号，假 FAIL 无法快速鉴别。Ch125 审计靠人工核对 trajectory 规避，不可持续。
2. **segment_audit 判定消费缺失**：`scripts/segment_audit.py` 退出码恒 0（observe 哲学，`halt_would_fire=true` 也返回 0），而 harness `run_audit`（`run_v10_ch200_climb.py:804-833`）只回收 returncode——段审计如果预测出 halt，harness payload 里没有任何字段反映，判定完全依赖人工读 JSON。Ch125 审计的 segment PASS 就是人工核对的。

两项都是评测/工具层，不改五门判定函数、不改生成链路。

## In Scope

- [ ] **F1 · five-gate health 报告章号透明化**：health 查询同时取 `checked_up_to_chapter`，`TargetMetrics` 新增 `health_report_chapter: int | None`；health 门 detail 携带该章号（如 `latest health 8.1 @Ch123 must be >= 8.0`）；JSON 输出同名字段。不改变任何判定逻辑。
- [ ] **F2 · harness 段审计 verdict 块**：`run_audit` 解析 five_gate JSON 的 verdict 与 segment_audit JSON 的 `halt_would_fire` / `critical_orphans`，在 payload 新增 `verdict` 块：`{five_gate: "PASS|FAIL", segment_halt_would_fire: bool, critical_orphans: int, health_report_chapter: int|null, stale_health_warning: bool}`。
- [ ] **F3 · stale health 预警**：`stale_health_warning = (health_report_chapter is not None and up_to - health_report_chapter >= 2)`；为 true 时 payload 附 `health_note`："health 报告可能滞后（192.aw 型），判 FAIL 前先补跑 continuity audit 到 <up_to>"。仅预警不阻塞。
- [ ] 单元测试：health 门输出含报告章号；run_audit verdict 块字段齐全（mock `_run_capture` 或用小 fixture DB 跑真实命令）；stale 边界（lag 1 不预警、lag 2 预警、None 不预警）。
- [ ] xuanhuan 冻结库复跑：five-gate @200 verdict 与 gates 判定不变（新增字段不改变 PASS 结论）。
