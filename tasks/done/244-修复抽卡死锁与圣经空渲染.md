## 目标

修复真实模型冒烟暴露的两个 P1 缺陷，恢复「抽卡 + continue 混用」与「实体/属性型 Canon 抽卡」两条作者主路径；顺带修空项目误导文案（发现 2）。不改 M0–M3 已接受的写径语义（Canon 三态、extract→pending、pick 只动 head 工作指针）。

## 背景与根因（冒烟实证，2026-11-11）

### 发现 5：pick→accept 后 `chapter continue` 永久 exit 2（死锁）

复现链（项目 A `90f4f35b…`，证据在冒烟目录 step1c/1d）：

1. `variant pick` → exit 0。M3 语义：pick 只改 `ChapterHead.current_version_id`，variant 行 status 恒留 `picked`（`variant_pick.py:100-117`，head 缺失时还会创建 head）。
2. `chapter accept` → exit 0。B2/B5：`accept_chapter` 单事务只做 accepted 副本 + head 双指针，**不动 variant 行**（`chapter_accept.py:1-8`，task 239 已接受语义）→ accepted 章残留 picked 槽（`chapter_continue.py:132-133` 注释自己标注此「可达形态」）。
3. `chapter continue`（下一章）→ exit 2：B1 前置①按「variant 行 status=picked 且章号 < target」拒绝（`chapter_continue.py:127-137`）。但章 **已** accepted，提示「请先 chapter accept」误导。
4. 出路 `variant abandon` → 也 exit 2：picked 槽拒绝 abandon（`variant_pick.py:151-154`「请先 pick 其它槽再 abandon」）；换槽 pick 只是把 picked 残留转嫁（旧槽仅 archived），无解。

**关键推论**：B1 口径下 target = 章宇宙第一个非 accepted 章，因此「章号 < target 的章必已 accepted」（代码注释原文）。B1 前置①按现状**只可能**误伤 accepted 章的残留槽，不可能命中其名义目标「picked 未 accept 的章」——该形态在 target 判定下不可达（未 accept 的章必为 target 或排在其前）。tech-m4 B1 原文：「picked 稿想进入可续写态，**唯一路径 = chapter accept**」——accept 完成后该章就是续写就绪态，残留槽不应再阻塞。故当前实现是 **B1 原文口径的实现偏差**，修法属 M4 范围内修正，不越 PRD。

### 发现 6：实体/属性型 Canon 的圣经文本恒空 → 抽卡必产垃圾

根因链（`src/songyan/plan_checks/bible.py`）：

1. `select_chapter_plan_bible_cards`（:159-177）：实体仅当被**本章 events 引用**（participants/causes/reveals_evidence）才入选。
2. `_render`（:253-254）：**无 events 且无 clues 时无条件返回空串**，无视已入选的实体/属性。
3. M2 extract→`canon confirm` 主路径只产 entity/attribute 提案（extract 属性窗口 = `valid_from_ch=1, valid_to_ch=None`，冒烟 DB 实证）→ **典型项目每章 `bible.text` 恒空**。项目 B 实证：confirm 24 条后 `load_chapter_plan_bible` 仍 `text_len=0`。
4. `variant_generate.py:81-89` 的抽卡写手 prompt 只吃 `bible.text`（M3 B 设计：只引用已批准 Canon）→ 产出占位/拒写/「（空）」回显，仍标 `status=generated`、exit 0、计费。项目 A 槽4 的 1337 字「成功」稿实为无视约束的幻觉。

**规格依据**：PRD :76「只有 `approval_status=approved` 的行进入本章事实圣经」（不限 kind）；PRD :415「写作和修订看见的事实圣经**等于本章 approved 计划卡**」；tech-m1 :126「在**章窗口规则允许时**出现在 `load_chapter_plan_bible`」。当前实现让 approved 实体/属性行进不了圣经文本，是 **实现低于 PRD 口径**，修法是达标修正而非改规格。fingerprint（`variant_fingerprint.py:108-129`）与圣经共用同一选择函数，修法同时让 `stale_vs_canon` 对实体/属性型 Canon 恢复意义。

## 方案设计

### D1（发现 5）：B1 前置①改按章级 accepted 判定 —— 推荐

- **修法 A（推荐，单文件）**：`chapter_continue.py` 前置①过滤条件改为「章号 < target **且该章 head 无 accepted_version_id** 且存在 picked 槽」。加载 heads 一次（`list_by_project`）得 accepted 集。按 B1 不变式，< target 的章恒已 accepted → 该守卫修复后实际不可触发，保留作防御。
  - 优点：只动 M4 自己的门禁；不改 task 239 已接受的 accept 事务（不动 variant 行）；不改 M3 pick/abandon 语义（避免触碰 tech-m4 §3.3「不改写 variant 语义」红线）。
- 修法 B（不推荐，备选记录）：`accept_chapter` 事务内把该章 picked 槽置 `archived`。
  - 缺点：给 accept 增加第三件事，违背 task 239「不动 variant 行」的已接受定义；触碰 M3 variant 行生命周期；同样要动 M3 abandon 守卫才能自洽。工作量大、越界风险高。

### D2（发现 6）：圣经入选规则 R1 + `_render` 去掉早退 —— 推荐

- **入选规则 R1（推荐）**：实体入选条件 = 被本章 events 引用 **∪** 拥有 ≥1 张**章窗口内**的 approved attribute（extract→confirm 流的载体就是 attribute）；attributes 仍要求实体入选 + `_in_window`。events/clues/anchors 逻辑不动。
  - 符合 PRD :76/:415（approved 行进圣经）与 tech-m1 :126（窗口规则保留）；章窗口语义不变（`valid_from/to` 照排）。
- 备选 R2（记录不取）：全部 approved 实体进每章圣经。会给长项目圣经注水（250 章 × 全量实体），与「本章圣经」口径冲突。
- **`_render`**：删掉 `if not events and not clues: return ""` 早退，按已选卡渲染（实体/属性段在 events/clues 缺席时也输出）。
- 连带影响（fingerprint 变好）：`select_chapter_plan_bible_cards` 输出集变化 → `parent_canon_fingerprint` 对实体/属性型 Canon 从「恒同」变为「随 Canon 演化」→ `stale_vs_canon` 恢复语义。这本来就是 M3 步 5 的设计意图。

### D3（发现 2，文案小修）

`cli/commands/chapter.py:166-168`：`continue` 返回 None 时分两种文案——章宇宙为空 → 「项目尚无章节工作稿；开章走 `run --chapters N` 或 `variant generate --chapter N`」；非空全 accepted → 保留「全部章已 accepted」。exit 0 不变（B11）。
